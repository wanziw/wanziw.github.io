[科研工具]科研skills汇总

发表于2026-09-19|更新于2026-09-19
|字数总计:3.5k|阅读时长:10分钟|阅读量:

从 Vibe Coding 到科研 Skills：我终于明白，AI 最强的能力可能是“模仿” 与其不停寻找“更聪明的模型”，不如把自己已经验证过的科研经验，整理成 AI 可以反复调用的 Skills。 六七月份那阵子，AI 和各种 Agent 更新得太快了。 我原来的用法其实很朴素：跟 AI 聊需求，让它写代码；复制到本地运行；报错了再把报错复制回去；让它改；再复制；再运行……一轮又一轮。 后来看到越来越多 Agent 开始强调“能直接干活”：能读写本地文件、能运行代码、能看到报错后自己修改，甚至还能接飞书、微信机器人。我当时想得特别美——如果这些事情都能自动完成，那我岂不是不用守在电脑前跑生信了？ 于是，我正式进入了一个很有科研特色的阶段：“自费科研模式”——自费给自己充各家 AI 会员。 后来才知道，这种“我说需求，AI 直接写代码”的工作方式有个名字：Vibe Coding。 几个月折腾下来，我现在已经比较稳定地把 Codex 当作生信分析助手。但也正是在这段时间里，我越来越清楚地意识到：模型很强，不等于它天然就懂你的科研。

  1. 把 AI 当 PI，效果往往没有想象中那么好 我曾经期待过一种特别理想的工作方式： 我只需要告诉 AI 一个研究问题，之后就让它像 PI 一样自己决定怎么分析、画什么图、怎么解释结果、怎么组织故事线。 现实是，即使模型已经足够强，这种全托管式科研依然经常差强人意。 代码可能能跑，图也可能能画出来，但“能跑”与“好用”中间还有很长一段距离。它未必知道我想要什么样的图，未必知道哪些结果在生物学上值得追，未必知道一组分析应该怎么前后衔接，更不会天然拥有我已经形成的审美和习惯。 我的项目其实已经整理得相当规整。 数据一般拆成 raw / processed / external；代码按功能拆成 0.func.R、1.scRNA.R、2.stRNA.R、3.crosstalk.R、4.enrich_score.R、5.trajectory.R、6.SCENIC.R……；中间结果保存成 RDS、xlsx、tsv、csv 放进 objects；快速预览的 png 和同名的 pdf/svg 矢量图统一放在 figures。 提示词也已经尽量压缩到“请用最简洁、高效且必要的代码分析执行”。 但这些还不够。 目录结构告诉了 AI 文件放在哪里，却没有告诉它我过去为什么这样分析；提示词告诉了 AI 要做什么，却没有给它足够多“我认为什么叫做好”的例子。

  2. 真正的转折：让 AI 参考我以前跑通的项目 有一次，我没有再从零描述一个新项目应该怎么分析，而是把自己以前已经跑通、而且我比较满意的研究项目代码给它参考，让它沿着旧项目的思路处理新数据。 效果突然就不一样了。 真的好很多。 那一刻我才反应过来：我以前其实一直在做一件很苛刻的事情——让一个刚进实验室、几乎不了解我的 AI，只看几十行或者几百行自然语言需求，就一次性“猜”出我积累了很多年才形成的分析习惯、代码风格、图形审美和研究逻辑。 这跟让一个刚入组的小白根据一页实验说明直接给你写出一篇 Nature，有什么本质区别？ 而当我把过去成功的项目交给它之后，问题就变了。 它不再需要猜。 它可以模仿。 AI 很强的一项能力，本来就是从已有模式中提炼规律，再把规律迁移到新的任务上。 这也让我重新理解了 Skill 的意义。

  3. Skill 不是“更长的 Prompt”，而是把经验变成可复用的工作流 我现在越来越觉得，未来很多专业工作并不是“给 AI 写一个神 Prompt”，而是把自己的专业经验一点点封装成 Skill。 一个真正有用的科研 Skill，至少应该告诉 AI 五件事： 输入是什么。 数据从哪里来，应该长什么样，哪些字段是必须的。 流程怎么走。 哪一步先做，哪一步后做，遇到什么情况需要分支。 什么叫正确。 需要做哪些统计检查、质量控制和异常判断。 什么叫好看、好读、好发表。 图的布局、字号、配色、导出格式，文章的逻辑、语气、句式和证据层级。 输出放哪里。 文件怎么命名、保存什么中间对象、最终交付哪些结果。 如果再往前一步，还应该把已经跑通的代码、优秀成图、目标论文、失败案例、修改记录一起放进 Skill，让模型看到“正例”和“反例”。 这时候 Skill 就不再是一个 Prompt 收藏夹，而更像是给 AI 写的一本实验室 SOP。 Prompt 解决的是“这一次怎么做”；Skill 解决的是“以后遇到这类问题，都按什么标准做”。

  4. 一个让我眼前一亮的例子：让 Codex 学会“怎么改 Discussion” 最近有一天，我几乎一整天都在改论文 Discussion。 我自己修改文章的时候，有一套很笨、但一直有效的方法：先找四五篇我认为写得好的论文，一段一段看它们怎么组织逻辑；再一句一句拆，看这句话是在陈述结果、补证据、解释机制，还是在收束结论；最后甚至会一个词一个词看，哪些词在表达观点，哪些词在转折，哪些词在控制语气强弱。 最后所谓的“写”，很多时候其实就是先把这些好文章的框架装进脑子，再回来改自己的稿子。 那天我突然想到：既然我是这样学的，为什么不让 Codex 也这样学？ 于是我让它先找一批高质量论文，不急着直接改我的文章，而是先学习： 高频的学术表达； 常见句式； Discussion 每一段承担的功能； 结果、证据、解释、局限、意义之间怎么过渡； 哪些表达属于谨慎推断，哪些属于过度解释。 然后把总结出来的规则、句式和逻辑框架整理成文本，再封装成一个专门用于论文修改的 Skill，并要求后续修改强制调用这套规则。 最终版本和“让一个空白 Codex 直接润色”的版本放在一起，对比非常明显。 这件事给我的启发比某一个具体 Skill 更重要： 任何高度专业、重复发生、又存在大量隐性经验的工作，都适合被拆成 Skill。

  5. 我目前整理的科研 Skills 地图 我把最近收集的一批科研 Skills 按实际工作流重新整理了一遍。这里不把“名字多”当成价值，而是按任务阶段去选。 文献检索与研究设计 nature-academic-search：文献检索、数据库与引用核验。 academic-research-suite：Codex 版的学术研究总入口，可覆盖原来的 deep-research、academic-paper、academic-paper-reviewer、academic-pipeline 工作流。 nature-reviewer：更适合用审稿人的视角反向检查研究问题、论证和证据。 阅读与汇报 nature-reader：论文全文阅读、拆解与解释。 pdf：通用 PDF 处理。 nature-paper2ppt：把论文整理成汇报结构。 nature-figure：科研图表设计、重绘与导出。 分析与结果解释 omics-analysis：我目前反而建议自己补建。通用的组学分析范围太大，与其安装一个名字相似但能力不匹配的 Skill，不如直接把自己已经跑通的 R/Python 生信流程做成专用 Skill。 manuscript-writing：从结果到论文叙述，适合帮助组织 evidence-to-claim 的故事线。 nature-data：与数据、表格和论文材料整理相关的辅助流程。 写作与润色 nature-writing：Nature 风格科研写作流程。 nature-polishing：论文语言、表达和提交前润色。 nature-citation：引用与文献相关检查。 ai-check：检查文本中常见的 AI 写作痕迹，可作为编辑提示，但不能把检测分数当作作者身份的证明。 aigc-down-skill：更偏中文学术文本的去模板化与人工复核流程。使用时仍应遵守期刊、学校或机构对 AI 辅助写作的披露要求。 humanize：与 ai-check 来自同一套社区 Skill，可把用户写作样本作为 voice matching 参考；这次把你写的 humanize / humanizer 统一映射为实际存在的 humanize。 投稿与返修 nature-response：拆 Reviewer 意见、补证据、组织逐条回复。 nature-reviewer：从审稿标准反查正文。 academic-research-suite：覆盖原 academic-paper-reviewer 的审稿/返修工作流。 另外，我截图里还收集到了 scansci-pdf、DyNote 这类工具型 Skill。它们不一定属于论文写作主链路，但很适合作为“信息进入科研工作流”的入口：一个负责文献获取，一个负责把视频/评论区等非结构化内容整理成可复用笔记。它们这次没有放进安装清单，后面可以单独做一期。

  6. 为什么我现在反而更想“手搓 Skill” 公共 Skill 很适合解决共性问题，但真正决定体验上限的，很可能还是自己的 Skill。 因为公共 Skill 不知道： 你习惯用 Seurat 还是 Scanpy； 你的单细胞对象怎么命名； 你喜欢什么图宽、什么字体、什么配色； 哪些中间结果必须落盘； 哪些图一定要同时输出 png 和 pdf/svg； 你过去哪套 trajectory、SCENIC、cell-cell communication 流程已经验证过； 你的课题组写 Discussion 时更喜欢怎样的证据顺序和语气强度。 这些东西对别人也许只是“个人习惯”，但对 AI 来说，恰恰是决定输出能不能直接使用的上下文。 所以我最近开始把过去已经优化过的提示词、跑通的输入输出、代码、图形模板、数据样式和备注逐渐整理进 Skills。 不是让 AI 替我思考，而是让它少在那些我已经想明白的问题上重新猜一遍。

  7. 我现在对“AI 科研自动化”的理解 以前我追求的是： 找一个更强的模型，然后告诉它需求，让它自己把事情做完。 现在我更愿意把问题拆成： 找一个足够强的模型，再给它一套经过真实项目验证的工作流、示例和判断标准，让它沿着这条路完成任务。 模型负责泛化，Skill 负责约束；模型提供能力，Skill 注入经验。 这可能也是为什么我现在越来越认同一句话： 未来的软件开发，很大一部分会变成 Skill 开发。 再往科研里翻译一下：未来真正拉开差距的，也许不是“谁最早订阅了最新模型”，而是谁能把自己的专业经验、实验室 SOP、代码资产和审美标准，持续沉淀成 AI 可以调用的能力。 医生会有医学 Skills，律师会有法律 Skills，科研人员也会慢慢拥有自己的科研 Skill Ecosystem。 而对我来说，这条路才刚刚开始。

  8. 这批 Skills 的安装核对结论 这次我按 Codex 的 skill-installer 逻辑重新核了一遍来源。最重要的一点是：截图里出现的这些名字并不都属于 OpenAI 官方 openai/skills。 官方可安装目录里，与这批目标直接对应的主要是 pdf；其余多数来自 Nature Skills、Academic Research Skills 以及其他社区仓库。 原目标 核对结论 本次建议 nature-academic-search 存在 安装 deep-research Codex 版已合并 用 academic-research-suite 覆盖 nature-citation 存在 安装 nature-reader 存在 安装，并安装 nature-shared academic-pipeline Codex 版已合并 用 academic-research-suite 覆盖 nature-reviewer 存在 安装 pdf OpenAI 官方存在 安装 nature-paper2ppt 存在 安装，并安装 nature-shared nature-figure 存在 安装 omics-analysis 没有足够可信的通用精确匹配 待补建 manuscript-writing 存在 安装 nature-writing 存在 安装，并安装 nature-shared academic-paper Codex 版已合并 用 academic-research-suite 覆盖 ai-check 存在 安装 aigc-down-skill 存在 安装 humanize / humanizer humanize 存在 映射为 humanize 安装 nature-polishing 存在 安装，并安装 nature-shared nature-data 存在 安装 nature-response 存在 安装，并保留 nature-shared academic-paper-reviewer Codex 版已合并 用 academic-research-suite 覆盖 我另外准备了一份 research-skills-install.sh。它会先检查 ${CODEX_HOME:-~/.codex}/skills，已经存在的自动跳过，只安装缺失项；omics-analysis 不会被硬装；humanize / humanizer 会统一映射为已核实的 humanize。执行完后会打印“新安装 / 已存在 / 失败 / 待补建”的结果。 安装完记得重启 Codex，再打开新的会话或查看 /skills 核对是否已经被发现。

配图建议 开头“从 App 到 Skill”的观点：放“未来的软件开发就是 Skill 开发”截图。 “代码能跑 ≠ 科研图好看”：放 Codex/Bizard 自动科研绘图截图及评论截图。 “科研 Skills 地图”：连续放三张“科研 Skills 速查表”。 “延伸工具”：放 scansci-pdf 与 DyNote 两张截图。 这样整篇文章会形成一条很清楚的叙事线：追模型 → 失望 → 找到模仿/参考范式 → 把经验做成 Skill → 建自己的科研 Skill Ecosystem。
